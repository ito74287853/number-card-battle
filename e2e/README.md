# E2Eテスト一式（number-card-battle）

ブラウザを自動で操作して、ゲームが仕様どおり動くかを確認する仕組みです。
**14ケース・所要2分弱**で、正常系から異常系まで一通り回り、
**説明を焼き込んだスクリーンショット**と**結果レポート**が自動で残ります。

```
node run.mjs          # 全ケース実行
node run.mjs T05 T06  # 指定したケースだけ
```

先に別ターミナルでゲームを起動しておいてください（`npm run dev -- --port 5199`）。

出力は `report/` に出ます。`report/report.md` が結果一覧、`report/T05/` などに証拠画像です。

---

## なぜ自動化するのか

手動テストで一番時間を食うのは、**確認そのものより「エビデンスを残す作業」**です。
画面を出して、スクショを撮って、ファイル名を付けて、どの項目のどの手順かを書いて、報告書に貼る。
1項目5分としても14項目で70分。しかも修正のたびに全部やり直しになります。

このスクリプトはそこを丸ごと引き受けます。**2分で14項目ぶんの証拠が揃い、
何度でも同じ条件でやり直せる**。回帰確認（前に直したものが壊れていないかの確認）が
「またやるのか」ではなく「走らせるだけ」になるのが本質的な差です。

## IDの決め方（採番ルール）

テストIDは **`<画面ID>-<連番>`**。画面IDは `screens.mjs` が正です。

```
SC01_TTL   タイトル画面        SC04_RES   結果画面
SC02_RUL   「遊び方」画面       SC05_RWD   報酬画面
SC03_BTL   バトル画面
SYS        画面をまたぐもの・非機能（リーク / レスポンシブ / JSエラー）
SPEC       仕様が未確定で、合否を出さず記録だけするもの
```

**画面IDに番号と記号の両方を入れている**のが要点です。

- **番号（SC01〜）** … 並べたときにゲームの流れどおりになる。記号だけだと `BTL` が `TTL` より前に来てしまう
- **記号（TTL / BTL）** … IDだけ見て何の画面か分かる

`report/` のフォルダ名は先頭に**実行順の連番**が付きます。

```
01_SC01_TTL-01/     ← タイトル画面の1件目
02_SC01_TTL-02/
03_SC02_RUL-01/
...
16_SPEC-02/
```

### 3つの決めごと

**① ケースはどの画面に置くか → 操作を始める画面**
「敵HPを0以下にすると勝利画面になる」は、操作するのはバトル画面なので `SC03_BTL`。
確認対象である結果画面は `touches: ['SC04_RES:勝利']` と書いて、**状態のカバレッジとして別に数え**ます。

**② IDは一度振ったら変えない**
過去の報告書と突き合わせる鍵になるからです。ケースを消しても**連番は詰めません**
（詰めると、過去のIDが別のケースを指してしまう）。

**③ 後から変わる属性はIDに入れずタグにする**
観点（機能 / 非機能 / 回帰 / 仕様確認）と優先度（smoke）はタグです。
重要度は状況で変わるので、IDに埋めると動かせなくなります。

```js
{ id: 'SYS-01', tags: ['非機能', '回帰', 'smoke'], ... }
```

```bash
node run.mjs --tag smoke     # 毎pushで回す最小限だけ
node run.mjs SC03_BTL        # バトル画面のケースだけ
node run.mjs SC03_BTL-04     # 1件だけ
```

★ この構造は **TestRail の Section（機能ツリー）＋ Type / Priority と同じ**です。
手で運用していた項目書を、そのままコードに写した形になっています。

### 画面IDを先に決めると、穴が機械的に分かる

`screens.mjs` に画面と**その画面が取りうる状態**を書いておくと、
ランナーが「テストが1件も無い画面」「一度も出していない状態」を数えて教えてくれます。

```
⚠️ カバレッジの穴
   - SC04_RES 結果画面 の状態が未テスト: 使いすぎで自滅 / 5ラウンド制覇
```

★ **手で項目書を作っていると、ここが一番抜けます。**
「勝ち」と「負け」は誰でも思いつきますが、「バーストで自滅」「5ラウンド制覇」のような
**滅多に出ない状態**は、一覧を先に作っておかないと発想に上がってきません。

### もうひとつの穴の見つけ方：画面 × 入力手段のマトリクス

このゲームは**マウスとキーボードの両方**で操作できます。それを表にすると抜けが出ます。

|  | マウス | キーボード |
|---|---|---|
| SC01_TTL タイトル | ✅ | ✅ |
| SC02_RUL 遊び方 | ✅ | ✅ |
| SC03_BTL バトル | ✅ | ✅ |
| SC04_RES 結果 | ✅ | ✅ Enter / ✅ Space |
| SC05_RWD 報酬 | ✅ カード / ✅ スキップ | ✅ 数字 / ✅ Enter |

★ **最初に作ったときは、この表の右下（報酬画面のキー操作）と、
結果画面のマウス操作・Space が丸ごと抜けていました。**
「キーボード操作を追加した」という変更に対して、
**追加した画面だけテストして、他の画面のキー経路を確認していなかった**のが原因です。

⚠️ **「新しく足した機能」でなく「足した機能が影響する範囲」で数える。**
入力手段のように**全画面に横断する変更**は、画面数ぶんの確認が要ります。

### いま、まだテストできていないこと（正直に）

**数値のロジックは、ほとんど検証できていません。**

- カードを使うと、敵HPが**そのカードの値ぶん**減るか
- 累積超過が**正しく足されて**いるか
- 選んだ報酬カードが**本当にデッキに入って**いるか

今は「画面が変わったか」「カードが薄くなったか」しか見ていないので、
**計算が間違っていても気づけません**。理由は単純で、canvas に描かれた数字を読む手段がないからです。

★ これが「テストしやすさはアプリ側の設計」の具体的な帰結です。
`battleScene.js` に3行足すだけで、この穴は一気に埋まります。

```js
if (import.meta.env.DEV) {
  window.__state = () => ({ round: this.round, enemyHp: this.enemyHp, totalOverflow: this.totalOverflow, deck: this.deck.map((c) => c.value) });
}
```

**テスト側をどれだけ工夫しても届かない場所がある**、というのは覚えておく価値があります。

## 3つのファイルに分けている理由

| ファイル | 役割 | 変更が必要になるとき |
|---|---|---|
| `cases.mjs` | **何を確認するか**（テスト項目書そのもの） | 仕様が増えた・変わったとき |
| `harness.mjs` | **どう操作し、どう観測するか** | 画面のレイアウトが変わったとき |
| `run.mjs` | **回して集計して証拠を残す** | ほぼ変えない |

分けている理由は、**変わる理由が違うから**です。

「報酬画面にボタンが増えた」ときに直すのは `harness.mjs` だけ。
「新しいテスト項目を足したい」ときに触るのは `cases.mjs` だけ。
これを1ファイルに混ぜると、レイアウトを変えるたびに全テストを書き直すことになります。

`cases.mjs` は、こう書けます：

```js
{
  id: 'T05', kind: 'test', seed: SEED_WIN,
  title: '敵HPを0以下にすると勝利画面になる',
  why: '勝利条件そのもの',
  async run(g, t) {
    await g.toBattle();
    await g.shot('バトル開始時');
    t.is(await g.playUntilResult(), 'battleResult', 'カードを使い切る前に結果画面へ移る');
    t.is(await g.resultKind(), 'win', '見出しが WIN! になっている');
    await g.shot('敵HPを0以下にした後：勝利画面');
  },
}
```

**座標もピクセルも出てきません。**「バトルへ行く」「結果が出るまで使う」「勝敗を読む」という
**業務の言葉**だけで書けています。この層を用意することを、実務では
Page Object パターン（あるいは Screenplay パターン）と呼びます。

## 効いている工夫（ここが手動テストとの差）

### ① 乱数を固定する

これが一番効きます。ゲームは毎回カードも敵HPも変わるので、そのままでは
**「たまたま勝った」「たまたま落ちた」**が混ざり、テストの意味がなくなります。

`harness.mjs` でページ読み込み前に `Math.random` を差し替えています。

```js
let a = seed >>> 0;
Math.random = () => { /* 決定論的な擬似乱数 */ };
```

これで**シードが同じなら毎回まったく同じ手札・同じ敵HP**になります。
おかげで「1ラウンド目に必ず負ける状況」のような、狙って作れないケースもテストできます
（`find-seeds.mjs` でシードを総当たりして、条件に合うものを探して固定しています）。

★ **「同じ操作をすれば同じ結果になる」状態を作るのが、自動テストの前提条件**です。
ここが揺れているテストは、落ちても直さず「もう一回流す」ようになり、やがて誰も信じなくなります。

### ② 観測できないものはテストできない

このゲームは canvas に絵を描いているだけなので、**DOMからは中身が一切見えません**。
ボタンも文字もHTML要素として存在しないので、普通のE2Eツールの「ボタンを探してクリック」が使えません。

そこで `harness.mjs` では**ピクセルの色を読んで**画面を判定しています。

```js
async phase() {
  if (await probe('purple', ACTION_BUTTON) > 500) return 'battleResult';
  if (await probe('purple', SKIP_BUTTON)   > 500) return 'reward';
  ...
}
```

動きますが、**かなり無理をしています**。実務でこの状況になったら、
まず考えるのは**アプリ側にテスト用の窓を1つ開けること**です。

```js
// battleScene.js に3行足すだけで、上のピクセル判定が全部いらなくなる
if (import.meta.env.DEV) {
  window.__state = () => ({ phase: this.phase, round: this.round, enemyHp: this.enemyHp, ... });
}
```

★ **テストしやすさ（testability）はアプリ側の設計に含まれる**、というのが要点です。
「テストが書きにくい」は多くの場合テスターの腕の問題ではなく、
**中身が見えない作りになっている**という設計の問題です。
これを言えるかどうかで、テスト担当者としての立ち位置がかなり変わります。

### ③ 合否を出さない「記録だけ」のケースを用意する

`S01` / `S02` は `kind: 'observation'` で、**合格も不合格も付けません**。

キーを長押ししたときの挙動は「直すか、仕様のままにするか」が未決なので、
**勝手に不合格にすると、判断していない人が判断したことになってしまう**からです。
かわりに事実だけを記録して、証拠を残します。

```
📝 S02  【仕様確認】報酬画面で数字キーを押しっぱなしにしたとき
      ・報酬画面で [1] を約1秒 長押しした後の画面: selecting
      ・→ 次ラウンドの1枚目が使用済みになっている（敵HPも削れている）
```

★ 実務でも「仕様確認中」の項目は普通にあります。**未決のものを未決のまま扱える**のは、
テスト項目書として健全な状態です。全部を○×に押し込もうとすると、判断が曖昧なまま数字になります。

### ④ 1件落ちても止めない

`run.mjs` は失敗しても次のケースへ進み、最後に集計します。
最初の1件で止まると、**1回流すごとに1個しかバグが見つからない**からです。
手動テストで「1項目NGでも残りは消化する」のと同じ考え方です。

### ⑤ 証拠に説明を焼き込む

スクリーンショットの上部に、ケースIDと手順の説明を描き込んでから撮っています。

```
T11 スマホ幅で縮小表示されてもタップ位置がズレない
3枚目だけをタップした後：狙い通り3枚目だけが薄い
```

★ **画像を1枚だけ切り出して人に見せたときに、それだけで意味が通る**ようにするためです。
report.md から切り離されても、LINEに貼っても、後から見返しても伝わります。

## ★ テストが落ちたら、まずテスト側を疑う

このスイートを作る過程で、**2回ともテスト側のミス**でした。

| 症状 | 実際の原因 |
|---|---|
| 「スキップボタンが反応しない」 | 前の手順で負けて別の画面に戻っていた。押していた座標は、その画面では別のボタンだった |
| 「起動直後がタイトル画面と判定されない」 | タイトルの「数字カードバトル」(40px) が x160〜480 に描かれ、**カード1枚目の判定領域(x121〜191)に食い込んでいた** |

どちらも**アプリは正しく、テストが間違っていた**。
自動テストは「動かないと言ってくる」ことがありますが、その主張が正しいとは限りません。
★ **落ちたときに最初に確認するのは、アプリではなくテストの前提**です。
（2件目の対策は `harness.mjs` の `phase()` にコメントとして残してあります）

## CIに載せる

`run.mjs` は**失敗があれば終了コード1**で終わります。これだけで CI に載ります。

**設定はもう入っています**（`.github/workflows/e2e.yml`）。
このPRをマージすると、**push するたびに自動でテストが走り、失敗したら赤くなる**ようになります。
証拠画像も成果物（artifact）として残るので、GitHub の画面からダウンロードして確認できます。

手元で試すのと違い、**忘れても勝手に回る**のが要点です。

★ ここが「テストを実行する人」と「テストの仕組みを作る人」の分かれ目です。
やっていること自体は今までと同じ確認ですが、**それが人手を介さずに回り続ける形になっている**かどうかで、
市場での評価がまったく変わります。

## ファイル一覧

| ファイル | 中身 |
|---|---|
| `run.mjs` | ランナー。実行・集計・レポート生成・終了コード |
| `cases.mjs` | テストケース定義（27件） |
| `screens.mjs` | 画面一覧（画面ID・画面の状態・遷移先）。IDの正 |
| `harness.mjs` | ゲーム操作と観測のAPI |
| `find-seeds.mjs` | 狙った状況になる乱数シードを総当たりで探す（1回だけ使う道具） |
| `browser.mjs` | Edge/Chrome を自動で探して起動する共通処理 |
| `github-actions.yml.sample` | CI設定のサンプル |
| `report/` | 実行結果（`report.md` ＋ ケース別の証拠画像） |

このフォルダは**単体で完結**しています。`npm install` してゲームを起動すれば、どこに置いても動きます。
